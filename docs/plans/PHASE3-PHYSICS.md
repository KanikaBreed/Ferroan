## 1. What the C# Jolt module does

### Binding and Jolt version

The region module does not call Jolt C++ itself. It calls `JoltPhysicsSharp` 2.19.1, which P/Invokes `joltc`. The native package is `JoltPhysics.Native` 1.0.4, pinned in `OpenSim.Region.PhysicsModules.Jolt.Backend.csproj` (lines 31–38). The recorded commit `ba2f3068c391d33788d33ebe53dc0ad4f7c15be4` is the JoltPhysicsSharp commit "Update to native libs, expose HeightFieldShapeSettings, bump version to 2.19.1" (10 October 2025). The matching joltc commit is `1715c5aab834` (10 October 2025, "Improve and add more bindings for HeightFieldShapeSettings"). Its CMakeLists fetches Jolt with `GIT_TAG v5.4.0`. The JoltPhysics.Native nuspec gives the same hash with a repository url pointing at joltc. The linux-x64 library is `libjoltc.so`, 2,046,568 bytes, dated 10 October 2025. It carries no version string.

Jolt release dates: 5.4.0 on 27 September 2025, 5.5.0 on 28 December 2025, 5.6.0 on 11 July 2026, 5.7.0 on 14 November 2026. The Pin8 native is the 5.4 generation. joltc `1715c5aab834` pins Jolt v5.4.0.

`JoltNative.cs` (1–338) loads one `joltc` per process, checks its SHA-256, and refuses an unrecorded file unless `[Jolt] AllowUnrecordedNative` is set. Every recorded build has `SafeForMultiplePools` false. The process-wide temp allocator note is `JoltNative.cs` 22–25: the stock library gives every physics system one process-wide temp allocator, so two `PhysicsSystem` updates at once stop the process. `ResolveJobPools(int)` at `JoltPhysicsBackend.cs` 389–391 only clamps the request. The overload that forces one pool on the stock native is `ResolveJobPools(int, JoltNativeInfo)` at 399–400.

That one-allocator limit belongs to the stock joltc which JoltPhysicsSharp 2.19.1 binds. It does not bind Ferroan. The 5.6 joltc which `oxijolt-sys` vendors has `JPH_PhysicsSystem_Update2` with an explicit `JPH_TempAllocator`, and its `joltc_ext` adds character updates that take one. Each `PhysicsSystem` can have its own allocator.

The module runs single precision (`Foundation.Init(false)`, noted in `JoltPhysicsBackend.cs` line 12 and in `JoltNative.targets`). The double-precision `joltc_double` binaries are dropped from the build output.

`DeterministicMode` defaults to false (`JoltConfig.cs` 43). The backend path at `JoltPhysicsBackend.cs` 1014–1023 only forces one worker thread and sets `DeterministicSimulation = true` explicitly. Left off, Jolt's own default still applies: true in 5.4 and 5.6. Jolt 5.7 removes the switch and is always deterministic. Body poses repeat run to run on one binary, including with several workers. What varies is the order of `OnContactAdded` callbacks from worker threads. `DispatchContacts` keeps the first report of a pair per heartbeat, so the contact point and the normal can vary. Body positions do not have to. The oracle runs with `DeterministicMode = true`, so the `OnContactAdded` order is fixed as well. With `CROSS_PLATFORM_DETERMINISTIC` on the same joltc and Jolt commits, those traces are bit-identical across platforms when Ferroan uses the same calls in the same order. `BaselineCheck.cs` treats rows as repeatable per build. The stock Windows file and the stock Linux file disagree because that native is not built with `JPH_CROSS_PLATFORM_DETERMINISTIC`. P3.0c regenerates the gate baselines. The `stock-1.0.4` files stay as the record of the 5.4 native.

`JoltPhysicsSharp` is MIT. `JoltPhysics.Native` and joltc are MIT (Amer Koleci). Jolt itself is MIT (copyright Jorrit Rouwe). Ferroan does not port the C# binding. It binds Jolt 5.6 through `oxijolt-sys` 1.6.0 (MIT OR Apache-2.0, copyright Artem Balashow). [NOTICE.md](../../NOTICE.md) carries the `oxijolt-sys` and Jolt texts, and the joltc text. `joltc_ext` revision 30 is MIT like joltc and is recorded there.

### What 5.6 changed, and what Ferroan can bind

Every published `oxijolt-sys` binds Jolt 5.6.0. That is 11 versions, from 0.4.0 (4 October 2026) through 1.6.0 (18 November 2026). It vendors joltc `886e0886` (13 July 2026) and Jolt `e77f1755` (v5.6.0). It compiles them from source, or downloads a SHA-checked prebuilt archive for x86_64 Linux (glibc 2.35), x86_64 Windows (MSVC 14.44) and aarch64 macOS. It has a `cross-platform-deterministic` feature, with prebuilt archives for that feature on all three platforms. There is no 5.4 build.

On the C# side, JoltPhysicsSharp has moved on: 2.22.0 (13 July 2026, the day joltc moved to Jolt 5.6.0) through 2.26.0 (19 November 2026, Native 1.3.0). joltc moved to Jolt 5.7.0 on 16 November 2026, so the newest C# packages are probably 5.7. The C# module can already load a non-stock joltc (`AllowUnrecordedNative`, and `JOLT_TEST_ACCEPT_UNRECORDED_NATIVE=1` in `TestNativeOverride`).

Jolt 5.6 changes the friction model. It also changes `CharacterVirtual`: a character could get stuck when teleported among steep slopes, could speed up beyond the requested speed when sliding along a wall low enough to trigger stair walking, and did not fully account for character padding. Kinematic-body islands changed as well. Walking, stairs and moving-platform traces therefore differ in a systematic way, not only by contact noise. Those are the gate's three areas: vehicles on the ground, walking, and resting contacts.

The maintainer has chosen option 2 in that deterministic form. Section 5 records it. Option 3 stays rejected. The stock linux/win spread was the interim gate only while the version was open. It is not the gate now. The `stock-1.0.4` baselines stay as the record of the 5.4 native. The gate baselines are the ones P3.0c regenerates.

### Threads, and how the region frame calls the scene

Jolt does not have a thread of its own in C#. `Scene.Heartbeat` (`Scene.cs` 1684–1716) starts one thread per region, `Heartbeat-(name)`. `Scene.Update` (1731–1823) calls `SceneGraph.UpdatePhysics` (`SceneGraph.cs` 222–224), which calls `PhysicsScene.Simulate(FrameTime)`, on that heartbeat thread. The shipped `FrameTime` 0.0909 comes from `RegionServerDefaults.ini` line 204 (`[Startup] FrameTime = 0.0909`), read at `Scene.cs` 1145. The constructor's 0.0908 applies only before the ini read (`Scene.cs` 863). Ferroan's frame already uses 0.0909 (`crates/ferroan-scene/src/frame.rs`).

Inside one heartbeat, before physics: terrain taint every fourth frame, `UpdateTerrain` every `m_update_terrain` frames. After physics: `CheckAtTargets`, moving-start/end, object-group updates, then `UpdatePresences` (the terse updates viewers see). Physics results of a heartbeat are visible to presence updates in the same heartbeat.

`JoltScene.Simulate` (`JoltScene.cs` 2786–2834) is the single-step path. The shipped path is the other one. `[Jolt] PhysicsStepRate` defaults to 45 in `JoltConfig.cs` (194) even when the key is left commented in `RegionServerDefaults.ini` (1417–1427). `JoltConfig.F` returns the default when the key is absent. `EffectivePhysicsStepRate` (361–379) keeps 45 whenever the rate times the heartbeat is at least one step. A 0.0909 s heartbeat is about 11 Hz, so the default is 45 Hz. `PhysicsStepRate = 0` is the single step per heartbeat.

`SimulateSubsteps` (3096–3156) and `SubstepAccumulator` (1–76). The order inside one substepped heartbeat:

- Once, first: rebuild dirty linkset compounds (`DrainDirtyLinksets`), answer queued camera rays (`DrainCameraRays`), activate bodies that were created inert (`DrainPendingActivation`).
- The accumulator adds the heartbeat time and takes as many steps of exactly 1/45 s as it holds, at most `MaxStepsPerFrame` (16). The remainder carries, in `double`. The step length is `(float)(1.0/45.0)`. Time past the cap is dropped and counted, not carried.
- At 0.0909 s × 45 = 4.0905 steps, that is 4 steps per heartbeat, and a 5 about one heartbeat in eleven. It does not alternate. The comment at `SubstepAccumulator.cs` 12, and the ini comment at 1418, say "alternate". That comment is misleading. P3.0 and P3.0b commit the exact count sequence from a zero carry.
- Keyframed motion runs once, for the time the heartbeat's steps cover (`StepKinematics(n * dt)` at 3119). A heartbeat that takes no steps leaves the pose.
- The vehicle clock is seeded on the first substepped heartbeat from `VehicleClock`, or from `DateTime.Now` when that delegate is null (`JoltScene.cs` 3127–3128). The oracle injects `VehicleClock`. A trace must not depend on the wall clock.
- Then each 1/45 s step, on the heartbeat thread: advance that clock, vehicle controllers, script forces, move and hover targets, then `IPhysicsBackend.Step`.
- `Step` (`JoltPhysicsBackend.cs` 5022–5106) takes the job-pool gate, then `_simLock` for the whole step (`StepLocked` from 5061). Under that lock it runs `StrikeAvatarsInTheWay`, `UpdateCastBySpeed` (per-step linear-cast motion quality by speed) and the sensor sweep (`BeginSensorSweep` / `FinishSensorSweep`, about 5112–5135), steps every `CharacterVirtual` first (`StepCharacter`, 4075), then `PhysicsSystem.Update` for rigid bodies. Characters see the world as it was at the start of that step. `Initialize` sets `VelocityIterations` to 20 (Jolt's own default is 10), `PositionIterations` to 2, and the sleep threshold and Baumgarte away from Jolt's defaults. Body caps are Jolt's defaults. Linear and angular damping default to 0.02 and 0.05 (`JoltConfig` around 40 and 95–105).
- Once, last: drain body and avatar state from the last step only, and dispatch the contacts of every step in the heartbeat as one set (`mergeSubsteps: true`). Viewers and collision events still update once per heartbeat. `Simulate` returns 1 on both paths.

With the 45 Hz path on, solver sub-steps come from `PhysicsStepCollisionSteps` (default 2), raised so each solver slice is at most 1/60 s (`CollisionStepsAt`, `JoltConfig.cs` 409–412). At 45 Hz that is 2, so the solver runs at 90 Hz. `CollisionSteps = 6` (the ini default) applies only when `PhysicsStepRate` is 0: six solver slices inside the one 0.0909 s update, and the character still steps once.

Jolt's own worker threads exist (`JobSystemThreadPool`, `JoltPhysicsBackend.cs` 87–120). They run inside `Update`. They are not the region heartbeat. On the stock native they are not safe for two physics systems at once. On Ferroan's joltc each system has its own allocator. One update at a time is still what the physics thread does, because D6 gives Jolt one thread.

Off the heartbeat thread, C# takes `_simLock` for `llCastRay`, avatar setup, and body create and remove (`JoltPhysicsBackend.cs` 4583–4597: the comment there calls the lock load-bearing). Ferroan's equivalent is the request queue in P3.3, not a second thread inside the native, and not a join of the physics thread.

### Actors

**Avatar.** `JoltScene.AddAvatar` (1044–1150) builds a `JoltCharacter` (`JoltCharacter.cs`). The body is a Jolt `CharacterVirtual`, not a solved rigid body (`JoltPhysicsBackend.cs` 3002–3036). A capsule: radius from the footprint, at least 0.2 m, cylinder half-height what remains of the box (`JoltCharacter.cs` 115–120). The default appearance box is 0.45 × 0.6 × 2.1 (the 1.9 m height plus the 0.2 m box adjust). Mass is 1.954922 scaled by capsule volume against that default (123–138). A kinematic query marker with the avatar's local id lets a ray find the capsule. `ScenePresence` writes `TargetVelocity`, `SetAlwaysRun`, `Flying` and a latched jump. The drain (`ApplyCharacterState`, 183) writes position, velocity and ground state back and requests a terse update. `IsColliding` is support. Ground is terrain when the supporting body is the terrain body or there is no body.

Entry points the scene calls on a live avatar, each with a row: `Position` (281, teleport within the region, and stand), `Size` (391, an appearance change rebuilds the capsule), `SetMomentum` (378), and push (`AvatarPushMaxSpeed`, `AvatarObjectPush*`, `StrikeAvatarsInTheWay`, `LooseObjectInStep` / `MoveOutOfCapsule`).

**Prims.** `AddPrimShape` (`JoltScene.cs` 1150–1176) cooks a shape and makes a `JoltPrim`. Non-physical prims are static. Physical prims are dynamic and are created inert, then activated at the start of the next simulate, after link weld and vehicle setup, so a reloaded vehicle does not free-fall (`JoltScene.cs` 2748–2810). Phantom is layer `Phantom`. Volume detect (`llVolumeDetect`) is layer `Sensor` and wins over phantom (`JoltPrim.cs` 50–54, 242–243). A selected physical prim is kept still (1857–1891). Grab is separate (`Grabbed`, 1833). A physical prim whose centre is below the terrain is lifted onto it before the body exists (`TryUnburyPhysicalLoad`, `JoltScene.cs` 3648–3664).

Live changes, each with a row: `IsPhysical` (1168–1200, `RecreateBody`, re-cook mesh against hull and cells), `Phantom` (2229), `SetVolumeDetect` (2215), `Size` (1141) and `Shape` (1155) through `Rebuild` and `CheckComplexity` against `[Jolt] MaxPhysicalComplexity`, `Position` (1046: `NoteMoveSet` turns a run of plain sets kinematic, `WakeWhatRestsOn`), `LockAngularMotion` (2150, `STATUS_ROTATE_*`), `AddForce` / `AddAngularForce` (2185, 2199, with `PushForceScale`), constant force and torque (`ScriptForceStepProvider`), move-to-target and hover (`JoltPrim.Targets.cs`, `BasicForcesStepProvider`), look-at (`JoltPrim.AngularTarget.cs`), keyframed motion (`JoltPrim.Kinematic.cs`, `StepKinematics`), materials (`SetMaterial` 1405, the InWorldz preset table, `Density` 1292, `GravModifier` 1436), and `PRIM_PHYSICS_SHAPE_TYPE` none, convex and prim.

**Linksets.** Each part is its own actor. `child.link(root)` (`JoltPrim.cs` 1991–2028) only marks the root dirty. `Simulate` welds before the step (`DrainDirtyLinksets`, `JoltScene.cs` 2768–2784): children become shapes in the root's `StaticCompoundShape`, and their own bodies go away (`RebuildCompoundNow`, `JoltPrim.cs` 2070). Collision identity of a child is the compound child's user data, so `llDetectedLinkNumber` is that link. Mass is the sum of each part's volume times that part's density (1345). A child script's buoyancy is forwarded to the root (`JoltPrim.cs` 1784–1794). A linkset of uncut boxes needs the body flags only. Cells inside a compound are a later case.

**Crossing and out of bounds.** `CrossingStart` (`JoltPrim.cs` 926) parks the body and keeps its velocity. `CrossingFailure` (944) puts it back 0.5 m inside the edge and 0.2 m up, and stops the motors. Out of bounds, the body is parked and core makes it non-physical. `MotorRunningState` is what a successful crossing would carry (age, direction, target of each motor). D38 defers an avatar walking across a border. A physical object or a vehicle can still reach the edge of a 256 m region. Failed crossing and out-of-bounds are Phase 3 (P3.56). A crossing that succeeds belongs with the avatar crossings that [D38](../DECISIONS.md) leaves for later, in Phase 4 (section 5, item 9).

**Attachments.** A worn attachment is not a second physics body in this module. `llSetForce`, `llApplyImpulse`, `llPushObject`, `llSetBuoyancy` and `llSetHoverHeight` on an attachment are applied to the wearer's `JoltCharacter` (`JoltCharacter.cs` 461–518, and the force path in `StepCharacter` 4099–4136). Dropping an attachment, or handing back a saved vehicle, goes through `JoltPrim.SetVehicle` (2382) and the normal prim add path. Grabbing and keyframed motion of an attached prim are the wearer's problem on the scene side. Phase 3 ports the wearer-side forces. The script calls that produce them arrive with Phase 4.

### Shapes

`JoltScene` cooking starts at 1186.

An uncut box, sphere or cylinder (no profile/path cut, hollow, twist, taper, shear, and path scale 100) is an analytic shape (`PrimHasNoCuts` 2224–2228, fast path 1229–1258): `CreateBoxShape`, `CreateSphereShape`, `CreateCylinderShape`. Anything else, and every sculpt or mesh, goes through the mesher.

The default physics shape type is `PRIM_PHYSICS_SHAPE_PRIM`. `JoltPrim.UseHullList` is `_isPhysical && _shapeType == PhysShapeType.prim` (`JoltPrim.cs` 262). `cellsWanted` is `!isMesh && isPhysical && useHullList && !IsSculptPrim` (`JoltScene.cs` 1293). A physical cut, hollow or twisted prim of that default type is cooked as `PrimHullCells`, not as one hull.

One convex hull is used in two cases only. The shape type is `CONVEX`, or the cell build fails and the caller keeps the single hull (`PrimHullCells` header: "the caller keeps today's single hull"). A non-physical prim is a triangle mesh. A triangle mesh of a physical prim would report volume 0 and mass 0 (`CookMeshShapeCore` 1710–1711), which is why the physical path does not stop on the triangle mesh.

`CookMeshShape` (1282) and `CookMeshShapeCore` (1546):

- A non-physical prim becomes a triangle `MeshShape`.
- A physical cut, hollow or twisted prim that is not a mesh asset and not a sculpt is `PrimHullCells.Build` (`JoltScene.cs` 1869–1910). The cells are the prim's real volume for mass. Which sector and span pair is chosen is whichever cooks cleanly in Jolt's hull builder and is closest in volume, so the cell set can change with the Jolt version. The oracle records the chosen pair and the cell count from the deterministic C# build, after the pin, and the port asserts those. Vertices stay within N ulp of the named `libm` calls.
- A mesh asset uses the hull list the asset already carries (`Mesh.ConvexHulls`), shared by asset id and size (`SharedShapeKey` 1314). A non-physical mesh whose physics shape type is convex stays a triangle mesh unless `[Jolt] HonourConvexMesh` is true (`JoltConfig.cs` 106–108). A non-physical mesh under 0.05 m on every side is a box (1556–1562). A mesh whose asset has not arrived yet stays a box and is recooked when the asset lands (`RequestMeshAssetIfNeeded`, 1181).
- A sculpt whose texture has not been fetched meshes to null and falls back to a box (1610–1612). The mesher builds an inverted sculpt inside out, as the viewer draws it, and the cook flips it for collision (1649).
- Identical cooks are cached. The mesher returns one shared `Mesh` instance per key. The scene copies vertices out and does not call `releaseSourceMeshData` on that instance (1571–1579).

`PrimMesher` is the geometry. `SculptMesh` / `SculptMap` are the sculpt image. There is no call into `ConvexDecompositionDotNet`.

`SculptMap` uses Skia only to downscale an image larger than `lod² × 4` pixels, with `SKSamplingOptions.Default` (61–75). It then samples every second pixel (108–112). At the physics LOD a 64×64 sculpt never reaches Skia. Larger images are downscaled by powers of two. P3.10a checks whether `Default` at SkiaSharp 4.153.1 is nearest-neighbour. If it is, the pixel-to-vertex step can be exact in Rust, and that row has no tolerance. The decode gap is JPEG 2000: C# uses CoreJ2K, Ferroan would use `j2k`. A fixture of pre-decoded pixels does not test that. P3.10b compares the two decoders on one lossless sculpt and one lossy sculpt.

### Avatar controller

`StepCharacter` (`JoltPhysicsBackend.cs` 4071–4249), once per 1/45 s physics step on the default path:

- **Walking.** Horizontal velocity is the requested velocity, scaled by the walk or run factor in `JoltCharacter` before it is stored. On walkable ground the avatar adopts the ground's horizontal velocity (a moving platform) and does not keep a slide from the previous step.
- **Flying.** `Flying` gives full 3D control. Gravity is off. Character mass for pushing objects drops to 0.001 so a flying avatar does not press a light object with a standing avatar's weight (4229–4235). Vertical speed uses the fly and fly-down factors.
- **Falling and landing.** On walkable ground, gravity is not accumulated, so the avatar stands on a slope inside `MaxSlopeAngle` (`OnGround`) and does not creep. In the air, or on steep ground (`OnSteepGround`, `IsSliding`), gravity is −9.80665 scaled by `(1 − buoyancy)`, applied as half a step before the move and half after if still in the air (4172–4246). Landing is the next step finding walkable ground and taking that ground's vertical velocity.
- **Jump.** A latch in `JoltCharacter` (51–55), because `ScenePresence` clears vertical intent before the step. Jump speed defaults to 4 m/s, and only from walkable ground (4158–4160).
- **Stairs.** `ExtendedUpdateSettings.WalkStairsStepUp` is the avatar's `StepHeight` along +Z (4223–4227). Jolt's character defaults are Y-up. The module remaps them to Z-up. Stick-to-floor is `stick = !hovering && (rec.Flying || gz < 0f)`, so it also applies while flying. The step-down is `max(0.05, StepHeight)`. The avatar does not step up onto a loose dynamic object in its path. It pushes that object (`LooseObjectInStep` 3228, `MoveOutOfCapsule` 3256).
- **Speed the viewer asked for** is still `ScenePresence.AddNewMovement` (about 4.096 m/s walk, four times that flying). The factors in `JoltConfig` are what make the controller match the documented metres per second. Phase 2 already stores that intent (`P2.2a`).

Jolt 5.6 changes stair walking, padding and the stuck-on-teleport behaviour of `CharacterVirtual`, and kinematic-body islands. P3.13b, P3.14b and P3.14c compare against the deterministic 5.6 build, so those changes are part of the oracle. They are not a reason for a tolerance.

### Vehicles

A vehicle is a physical prim whose actor owns a `VehicleController`. Parameters and flags enter through `PhysicsActor` (`JoltPrim.VehicleFloatParam` and the three siblings, 2335–2361) and through `SetVehicle` for a saved record (2382). The controller runs at the start of each 1/45 s step (`StepVehicles` inside `SimulateSubsteps`), and a `VehicleStepProvider` applies the resulting force during `PhysicsSystem.Update`.

Types (`VehicleProperties.cs` 139–151): none, sled, car, boat, airplane, balloon, plus InWorldz motorcycle (LSL 10002) and sailboat (LSL 10001).

Flags (`ExtendedVehicleFlags`, 158–184) use the OpenSim `VehicleFlag` bit values through `LockRotation` (32768), then Halcyon extensions: `LimitMotorDown`, `TorqueWorldZ`, `MousePointSteer`, `MousePointBank`, `ReactToWind`, `ReactToCurrents`. Standard names: `NoDeflectionUp`, `LimitRollOnly`, `HoverWaterOnly`, `HoverTerrainOnly`, `HoverGlobalHeight`, `HoverUpOnly`, `LimitMotorUp`, `MouselookSteer`, `MouselookBank`, `CameraDecoupled`, `NoX`, `NoY`, `NoZ`, `LockHoverHeight`, `NoDeflection`, `LockRotation`.

Float parameters (83–104): the usual LSL deflection, banking, buoyancy, hover and vertical-attraction values, plus InWorldz `InvertedBankingModifier`, `MouselookAltitude`, `MouselookAzimuth`, `BankingAzimuth`, `DisableMotorsAbove`, `DisableMotorsAfter`. Vector parameters (112–125) keep a timescale per axis, which is the Halcyon model, plus wind efficiencies. One rotation parameter: the reference frame.

`[Jolt] VehiclePresets` defaults to `Documented` (the wiki presets). `[Jolt] VehicleBehaviour` defaults to `InWorldz` (`JoltConfig.cs` 65–66, `RegionServerDefaults.ini` 1439–1448). The ini comment lists where those differ: a tenth of pitch righting kept on cars, boats and sleds under `LimitRollOnly`, hover-up behaviour while buoyant, and friction that would push a vehicle upward being dropped. `VehicleGroundGravityFactor` defaults to 1 (full gravity on a car or sled that is touching something). Sled contact friction defaults to 0.

`ReactToWind` and the wind-efficiency parameters sample `IWindModule` (`VehicleStepProvider.cs` 48 and 178; `VehicleWindTests`, `VehicleBalloonWindTests`; harness `balloontest` drift). Phase 3 does not port a wind module. Region wind stays zero, and a wind module waits for a later phase (section 5, item 10). P3.23d still runs the law against an injected wind sample, so the force is tested.

Boat and balloon buoyancy, hover height and water level (`SetWaterLevel`, `JoltScene.cs` 3691–3694) are the first vehicle behaviours a viewer notices. Linear motor, angular motor, banking and deflection are the rest of `StepCore`. The controller itself compares exactly through `IVehicleBody` (section 3). The engine trace is only the integration.

### Buoyancy

`llSetBuoyancy` on a prim stores a factor. The body's gravity factor is `(1 − buoyancy) × gravity multiplier`, clamped (`JoltPrim.cs` 1607–1818). InWorldz behaviour maps 0.977 up to 1 onto 1. A vehicle ignores the prim's `llSetBuoyancy` and uses `VEHICLE_BUOYANCY`. The value is kept for when the vehicle type is cleared. On an avatar, the same `(1 − buoyancy)` scales gravity, and it does nothing while flying or hovering (`StepCharacter` 4089–4091, `JoltCharacter.cs` 499–518). Water height is a separate input for vehicle hover (`HoverWaterOnly`), stored by `SetWaterLevel`. Buoyancy itself is a gravity scale, not a fluid force.

### Collision events

`DispatchContacts` (`JoltScene.cs` 3237–3416) runs on the heartbeat thread after the drain. Each subscribed prim gets one `CollisionEventUpdate` listing local ids it touches this heartbeat. Terrain is local id 0. `SceneObjectPart.PhysicsCollision` diffs that set against the previous heartbeat and fires `collision_start`, `collision` and `collision_end`. `llDetected*` reads the list. A pair that begins and ends inside one heartbeat still counts as a start, then an end on the next heartbeat. Contacts from the inner steps are merged. A pair is counted once.

`ShouldDeliverToPart` (`CollisionFrameTracker.cs` 58, `MinRepeatSeconds` 0.13) throttles a repeated `collision` to about 0.13 s. A frame whose contact buffer overflowed does not emit `collision_end` for the pairs it failed to see.

Delivery is to the struck part (compound child), and the other side is named by the body (a physical linkset by its root). Volume-detect contacts go only to the detector. Avatar contacts name land as 0 and an object by its root. Two avatars each hear the other, because Jolt reports the contact on only one character update (3355–3362). A contact whose normal points down is the feet, and becomes the collision plane under the avatar. Relative speed along the normal feeds collision sounds (above 0.2 m/s) and impact damage (below −5 m/s).

A pair that is missing this heartbeat only because both bodies slept is held (`StillTouchingAsleep`, 3541–3549), so a resting object does not get `collision_end` when it falls asleep. `GetTopColliders` (3705–3718) returns up to 25 prims by contact count.

Phase 4 is what runs the script events. Phase 3 produces the same `CollisionEventUpdate` the scene would hand to `SendCollisionUpdate`, and the collision plane on the avatar terse update. Replaying a recorded `ContactReport` array through `CollisionFrameTracker` and `DispatchContacts` compares those sets exactly, and that replay does not need the native. A point and a normal that come from the engine are part of the exact trace: the oracle runs with `DeterministicMode = true` on the deterministic joltc, so the callback order is fixed and the floats match across platforms.

P3.18a is a box against terrain and a box against a box, and it follows the body-flag row. Linkset identity and avatar pairs are later slices of the same dispatch.

### Ray casts

`SupportsRaycastWorldFiltered` is true (`JoltScene.cs` 2247). That is the flag `ScenePresence.MakeRootAgent` checks.

Two world entries (`2274–2284`):

- The 4-argument cast is a script `llCastRay` (Phlox). Filter is terrain, static, dynamic and avatar. Phantom and sensor are excluded. Charged to the script budget. A budget miss throws `RayCastTimeExceededException`.
- The 5-argument cast takes `RayFilterFlags`. Callers are rez placement (`Scene.GetNewRezLocation`), the arrival landing ray (`ScenePresence.MakeRootAgent`, `ScenePresence.cs` 1543–1602), and YEngine `llCastRay`. Charged to the simulator budget. A miss returns no hits.

`RaycastActor` (2293) is the sit query: one part, including a welded child as its own shape.

The viewer camera ray is a third path. `SupportsRayCast` is overridden at `JoltScene.cs` 2679: `CameraRayBudgetMs > 0`, and that budget defaults to 30 (`JoltConfig.cs` 162–163). The override at 2681 queues the ray. `DrainCameraRays` answers it at the start of each simulate, against `RayFilterFlags.AllPrims`, closest hit. `ScenePresence.checkCameraCollision` turns the hit into the camera constraint plane sent to the viewer. `AnswerQueuedCameraRaysWithMisses` answers a miss when the region goes down. The comment at `JoltScene.cs` 2272–2273 says the module does not override `SupportsRayCast`. That comment is stale and contradicts 2679. [TRANQUILLITY_BUGS.md](../TRANQUILLITY_BUGS.md) records behaviour, not comments, so the defect is noted here and Ferroan follows the override. P3.17 is this ray.

Budgets are `[Jolt] RayCastBudgetMs`, `RayCastSimulatorBudgetMs`, `RayCastMaxTestedHits` and `RayCastMaxHits` (cap 256). They reset every heartbeat (`BeginRayCastBudget`, `Simulate` 2794).

The arrival ray casts down from above the arrival point with `RayFilterFlags.PrimsNonPhantomAgents` when the arrival is not carried, the landing point was not moved, and the engine supports filtered rays. The newcomer stands on the first prim or avatar capsule hit. A second avatar at the same point stands on the first, about 2 m up. BasicPhysics returns false from `SupportsRaycastWorldFiltered` (`PhysicsScene.cs` 347–350), which is why the Phase 2 stand-in has no ray and why a `--physics basicphysics` capture lands at ground height.

`Scene.GetNewRezLocation` uses the 5-argument cast. P2.8a puts a new rez on the terrain as the stand-in (D38). P3.16b is the row that switches rez placement to the physics ray.

### Terrain heightfield

`SetTerrain` (`JoltScene.cs` 3552–3613) takes the region's `float[]` in OpenSim order, `heightMap[y * sizeX + x]`. It builds an `(N+1)` square field so the heightfield spans the far edge. A 256 m region becomes 257 samples at 1 m. Non-square regions pad to `max(sizeX, sizeY) + 1` by repeating the last sample. `CreateHeightFieldShape` plus `SetTerrain` swaps the terrain body. The `(N+1)` expansion is exact arithmetic and does not need a tolerance.

`TerrainHeightAt` (`JoltScene.cs` 197–210) is a bilinear blend of the input samples. Jolt's heightfield is two triangles per cell, quantised to `BitsPerSample` (Jolt's default is 8) per block. They agree at sample points and differ inside a non-planar cell. A downward ray at integer metres is a fair compare. An off-grid hover height is not a compare against `TerrainHeightAt`.

A terrain edit lifts avatars that would be buried (`ReGroundAvatarsOnTerrainChange`, 3672). It does not pull avatars down. `TerrainModule` calls `SetTerrain` on a tainted edit (`TerrainModule.cs` 958, about every 5 s) and then swaps the body. An estate water change calls `SetWaterLevel` (3691–3694). P3.2 is a static flat field. P3.2d adds slope and hill. P3.2e is the runtime swap and the water change. The buried-avatar lift is a case on P3.14a, because it needs a character.

The heightmap Ferroan already loads (`P2.0e`, `P2.0e2`, `P2.0e3`) is this array.

### Time dilation and the stats that must stay put

`JoltScene.TimeDilation` (2923) is a window of 11 heartbeats, from the real gap between `Simulate` calls. It feeds `Scene.TimeDilation` (`Scene.cs` 534). The client view writes it into object updates and terse updates, and into `SimStats`. Ferroan hard-codes 1.0 (`0xffff`) in `crates/ferroan-client/src/appearance.rs` (91–92), `crates/ferroan-client/src/entity_feed.rs` (80) and the assertion in `circuit_tests.rs` (2348), because BasicPhysics returns 1. With Jolt, the dilation field on those packets follows load. P3.3b injects the clock (`HeartbeatClock` on the C# side). The value is wall-clock driven.

`Simulate` returns 1 per heartbeat on both the single-step path and the substepped path, so `SimStats` physics FPS stays at the heartbeat rate under 45 Hz substepping. `SimPhysicsStepMs` is hard-coded 20 (`SimStatsReporter.cs` 390). Neither becomes 45.

## 2. What Ferroan has today, and what Phase 3 replaces

`ferroan-physics` holds the substep accumulator (P3.0b), the `[Jolt]` reader (P3.2c) and, since P3.1, the Jolt bind. A heartbeat past 16 steps reports `physics.steps-per-frame`. The crate root denies unsafe. The `native` module is where this crate allows it, and `ferroan-scripting` may once that crate exists. The workspace forbids unsafe code everywhere else. Only `ferroan-physics` depends on `oxijolt-sys`. [NOTICE.md](../../NOTICE.md) has the `oxijolt-sys`, Jolt, joltc and `joltc_ext` notices. The vendored-fork fallback is beside [D8](../DECISIONS.md).

What touches motion today:

- **Terrain heights.** `ferroan-scene` loads the heightmap as C# `Scene.LoadWorldMap` does: the `terrain` row, else `bakedterrain`, else `[Terrain] InitialTerrain`, on SQLite, MySQL and PostgreSQL (`P2.0e`, `P2.0e2`, `P2.0e3`). The frame samples it for login and teleport landing and for the walking stand-in. Phase 3 keeps that array and also cooks it into a Jolt heightfield. The interpolated height used at login stays the scene's until the arrival ray replaces the "land on the ground" part of that rule.
- **The frame thread.** One thread, `FrameTime` 0.0909, no drift (`P2.1a`, [D6](../DECISIONS.md), [D39](../DECISIONS.md)). It owns presences and stored prims. Circuits post `AgentUpdate` and do not block on the thread. After each tick it applies terse thresholds and queues viewer updates. Phase 3 does not move that thread. It adds a second thread for Jolt. The frame posts one heartbeat and waits for the poses before it samples them for terse updates, so a viewer still sees the post-physics position in the same tick. The wait is a channel or barrier hand-off. The physics thread is not joined. The sample-window race R29 fixed (a frame tick landing between the root report and the arrival sample) is the kind of hole this hand-off has to keep closed.
- **How other threads reach Jolt.** C# takes `_simLock`. Ferroan keeps every Jolt call on the physics thread. The frame, a circuit task that creates or removes a body, and a script `llCastRay` post a request on that thread's queue and wait for the reply. P3.3 is that queue. A mutex that let the frame thread call Jolt would put Jolt calls on a second thread, which D6 does not allow.
- **Movement intent.** `P2.2a` stores `AgentUpdate` as target velocity, fly, always-run and the control flags, with C#'s significance filters. Phase 3 feeds that intent to the character controller instead of to the stand-in. The speed factors, the jump latch, and the split of buoyancy and gravity are pure and compare exactly (P3.13a).
- **The walking stand-in.** `crates/ferroan-scene/src/walk.rs`, from BasicPhysics `Simulate` (`P2.2b1`, `P2.2b2`). Each tick, X and Y move by velocity times `FrameTime`. Z is the integer terrain cell plus the 2.1 m box while walking, a fall to that height, or a held Z while flying, with a snap when flight would go through the ground. Prims are ignored. There is no collision plane (`frame.rs`). `fixtures/walk/walk.cap` is a `--physics basicphysics` capture, and the stand-in matches those positions bit for bit. The live walk scenario uses that flag on the C# region. Ferroan has no physics switch ([LIVE.md](../LIVE.md)). The live harness has `--physics basicphysics` today. P3.15 adds a Jolt switch and sets meshing to `Meshmerizer`.

Phase 3 deletes the stand-in ([D38](../DECISIONS.md)) once the character controller matches a Jolt capture of the same walk. Until that row, the stand-in still moves avatars, and Jolt can already be stepping a falling box on the other thread. The two must not both write an avatar's position.

Stored prims (`P2.4a`, `P2.5a`) are scene objects with a physics flag and a shape. They do not collide and they do not move. `P2.8a`, `P2.8b1` and `P2.8b2` store `ObjectFlagUpdate`, `ObjectShape` and scale, and do nothing until Phase 3. The actor rows (P3.40 onward) are what wire those producers to the body. Terse updates for prims already have a queue (`P2.5a`). The physics drain is a new producer on that queue.

Water height and region settings (`P2.4c`) are the water level `SetWaterLevel` needs. Parcel and permission work does not block physics. Animations (`P2.3b1`, still TODO) read "on ground" from the stand-in's colliding flag today. After the stand-in goes, that flag is the character's `IsSupported`. Whichever of P2.3b1 and P3.15 lands second does that move. P3.15 does not implement animations.

The arrival landing rule in the scene is the only copy, and it has no ray ([PLAN.md](../PLAN.md)). Phase 3 adds the ray beside that rule and lands on the first hit. Comparisons of arrival against a C# region stay on `--physics basicphysics` until that fixture exists. The harness default C# engine is ubODE, which does cast the ray, so a default C# arrival is the wrong oracle for Ferroan until both sides run Jolt with meshing `Meshmerizer`.

Time dilation on the wire is the constant 1.0 cited above. P3.3b replaces that constant with the scene's value.

## 3. Proving equivalence with C#

### The oracle is the harness

`Tests/JoltPhysicsHarness` (`Program.cs`) runs Jolt physics scenarios with no region, at chosen heartbeat rates. Every run is built as the simulator builds it: shipped `[Jolt]` config, `physics = Jolt`, `meshing = Meshmerizer` (`Harness.cs` 1854–1855), the region mesher, and a warm-up step. It writes per-heartbeat traces and `summary.csv`. The named scenarios include `car`, `sled`, `boat`, `airplane`, `balloon`, `hover`, `attract-roll`, `attract-pitch`, `mouselook-turn`, `avatar-stand`, `avatar-walk`, `avatar-run`, `avatar-fly`, `avatar-jump`, `avatar-platform`, `push-avatar`, `push-box`, `push-car`, `drop`, `park-*`, `crash-*` and `raycast-cost`, plus the cases in `GrabScenarios`, `KinematicScenarios`, `PhantomScenarios`, `ContactScenarios` and the other harness files. `ci/runs.txt` records runs. `ci/baselines/stock-1.0.4-{linux-x64,win-x64}/` are the 5.4 native's rows, and the two files disagree. P3.0c regenerates the gate baselines on the deterministic joltc.

`tools/jolt-oracle` is a thin wrapper. It runs that harness and converts the traces to committed JSON. It is not a second scene builder. The harness's own default is `--physics-rate 0`. The wrapper passes `--physics-rate 45`, sets meshing to `Meshmerizer`, injects `VehicleClock`, and sets `DeterministicMode = true`.

`cargo xtask jolt generate` and `verify` run it. Ordinary CI does not. The Linux live workflow can, the way it runs the other oracles. Rust tests replay the committed JSON on every platform and skip, with a printed reason, when the native library for that platform cannot be built. [D13](../DECISIONS.md) names each allowed C# oracle (reference, schema, config, http, asset, griduser, regionstore, shard and walk). P3.0 adds `jolt`. [TESTING.md](../TESTING.md) already says a documentation-only pull request does not start a server, and that native crates get `SAFETY` comments and fuzzing of the boundary.

P3.1 and P3.3 need no C# oracle. P3.1 is the crate. P3.3's overlap test is a unit test.

### What compares exactly, with no native

These do not link Jolt. They are the first rows in the queue. They do not wait on the pin.

- **`SubstepAccumulator`.** The integer step-count sequence over 1,000 heartbeats of `0.0909f` from a zero carry, and the capped case (`MaxStepsPerFrame` 16, excess time dropped and counted). Exact integers. A float-width mistake fails it.
- **`CollisionFrameTracker` and `DispatchContacts`.** Replay recorded `ContactReport` arrays. The resulting `CollisionEventUpdate` sets match exactly: local ids, phase, heartbeat index. Terrain is 0. ### What the engine traces compare

Every Jolt-backed row is an exact trace against the deterministic C# build. Both sides make the same API calls in the same order. The oracle runs with `DeterministicMode = true`. ### Risks

- **Jolt version, decided.** Option 2, in its deterministic form. Pin8 is joltc `1715c5aab834` (Jolt v5.4.0). The oracle moves to joltc `886e0886` and Jolt `e77f1755` (v5.6.0), through JoltPhysicsSharp 2.22 or later on that generation. Both sides move Jolt together after that, and fixtures regenerate at each move. A 5.7 package is the wrong generation for this pin. The call order has to match the C# order. Friction, `CharacterVirtual` and kinematic-body islands in 5.6 are part of the oracle.
- **Floating point.** `FrameTime` is a C# `float`. The accumulator uses `double` for the carry and `float` for the step length. Gravity is the float −9.80665. A Rust port that promotes a step to `f64` and comes back will drift. P3.0b fails on that. Geometry rows name the `libm` calls.
- **Threading.** C# runs simulate on the heartbeat thread and Jolt workers inside `Update`. Ferroan runs the frame and Jolt on two threads ([D6](../DECISIONS.md)). The frame waits on the reply before it reads poses. The sample-window race R29 fixed is the failure mode of sampling too early. Two regions in one process are not the current Ferroan shape. Ferroan's joltc can give each system an allocator. The physics thread still runs one heartbeat at a time.
- **Step order.** Shipped order is linkset weld, camera rays, pending activation, keyframed motion once for the covered time, then for each 1/45 s step: vehicles, script forces, targets, character, solver, with the sensor sweep and the cast-by-speed update inside the step. Reports once per heartbeat, contacts merged. An oracle that steps once per heartbeat (`PhysicsStepRate = 0`, the harness default) will not match a region running the default. The wrapper passes 45.
- **Settings the first traces depend on.** Solver iterations 20 and 2, sleep threshold, Baumgarte, damping 0.02 / 0.05, `CollisionStepsAt` 2 at 45 Hz, injected `VehicleClock`, `StrikeAvatarsInTheWay`, `UpdateCastBySpeed`, the sensor sweep. Leaving any of these at Jolt's own default makes the first box diverge for a reason that is not the port.
- **Character versus body.** Characters step before the solver and are not in it. A test that expects an avatar to be a dynamic capsule will not match.
- **Mesher pixels and D11.** Sculpt images go through SkiaSharp only for the downscale described above, and through CoreJ2K for JPEG 2000. Ferroan cannot add Skia ([D8](../DECISIONS.md)). `aurora-prim` is the wrong substitute for `PrimMesher`. Convex cells (`PrimHullCells`) are what a physical cut prim uses. Substituting parry3d V-HACD changes hull count, mass and contacts.
- **InWorldz vehicle defaults.** `VehicleBehaviour = InWorldz` with `VehiclePresets = Documented` is the shipped combination. A port that follows only the wiki will fail the boat and car telemetry.
- **Build download.** `oxijolt-sys` downloads a SHA-checked archive at build time for x86_64 Linux (glibc 2.35), x86_64 Windows (MSVC 14.44) and aarch64 macOS 11.0. That is a network fetch of native binaries during `cargo build`. The repository default is `JOLTC_PREBUILT=require` without `force`, so CI and a default build use that archive. `JOLTC_PREBUILT=off` builds from source. `JOLTC_LIB_DIR` is refused. The recorded SHAs move with the `oxijolt-sys` version. P3.1 records the choice beside D8. Open question 12 is decided.
- **Young dependency.** `oxijolt-sys` is about seven weeks old, from one publisher (`pockerhead/oxijolt`), with 11 releases. [AGENTS.md](../../AGENTS.md) §6 asks for maintained, justified dependencies. Jolt 5.7.0 (14 November 2026) is out and the crate has not followed. The vendored-fork fallback is beside [D8](../DECISIONS.md). Open question 13 is decided.

## 5. Questions

All thirteen are decided. Items 5, 8, 12 and 13 were settled by the maintainer on 26 November 2026. Items 2, 3, 4, 6, 7, 9, 10 and 11 are manager defaults from that day; the maintainer may override them. Each item names the rows that change.

1. **Jolt version. Decided by the maintainer.** Option 2, in its deterministic form. Rows: P3.0c, P3.0d and P3.0e. P3.0e writes the entry under the next free id in [DECISIONS.md](../DECISIONS.md). The number stays here so later questions keep theirs.

   - **Option 2, chosen.** Tranquillity's Jolt module moves to JoltPhysicsSharp 2.22 or later, on the 5.6 generation whose joltc ABI matches `oxijolt-sys` 1.6.0. Check which package commit carries joltc `886e0886` and Jolt `e77f1755`. Adapt `JoltPhysicsBackend.cs` to the binding changes since October 2025. The C# oracle, and the shipped module where that is practical, loads a joltc built with `CROSS_PLATFORM_DETERMINISTIC` from those commits. Ferroan builds `oxijolt-sys` with `cross-platform-deterministic`. The same API calls in the same order give bit-identical traces, provided Ferroan creates bodies, shapes and settings in the C# order. A Jolt commit pin goes in [REFERENCES.md](../REFERENCES.md). Fixtures regenerate at each later move. Both sides move Jolt together from then on. P3.0e also updates the PLAN gate line to say the tests are bit-identical traces against that C# build.

   - **Option 1, not chosen.** Keep Jolt 5.6 in Ferroan and compare engine traces with a tolerance, with no C# change. The 5.4 to 5.6 friction and `CharacterVirtual` changes would sit inside that tolerance. It is not the gate.

   - **Option 3, rejected.** Point Ferroan at the 5.4-generation joltc. No `oxijolt-sys` release binds 5.4.

2. **Convex decomposition. Decided by the manager.** PLAN's building-block table names parry3d's V-HACD. The Jolt module never calls `ConvexDecompositionDotNet`. Physical concave prims use `PrimHullCells`. The rows port `PrimHullCells`. parry3d is Rust, so it does not need a [D8](../DECISIONS.md) exception. When P3.9 lands, correct PLAN's Convex decomposition building-block line to `PrimHullCells`. The line stays as it is until then. Row: P3.9.

3. **Sculpt pixels. Decided by the manager.** P3.10a checks whether `SKSamplingOptions.Default` at SkiaSharp 4.153.1 is nearest-neighbour, and if it is, the vertex step is exact. P3.10b compares CoreJ2K with `j2k` on one lossless and one lossy sculpt. If those pixels differ, P3.10b blocks until a decoder matches. Sculpt pixels decide collision shapes. Row: P3.10b.

4. **Safe `oxijolt` crate. Decided by the manager.** The rows depend on `oxijolt-sys` directly. The safe `oxijolt` crate stays out of `Cargo.toml`. A dependency used only by `ferroan-physics` would satisfy the one-crate rule, so that rule is not the reason. The deterministic compare needs Ferroan to control the order of Jolt calls and settings, and a wrapper can add calls of its own. Its unsafe code would also sit outside Ferroan's `SAFETY` review. Rows: the standing decision above, and P3.1.

5. **Vehicle behaviour. Decided by the maintainer on 26 November 2026.** Ferroan's region default stays `VehicleBehaviour = InWorldz` with the shipped presets, as C# ships: `VehiclePresets = Documented` and `VehicleGroundGravityFactor = 1`. The gate follows those. Rows: P3.19 and the vehicle rows that read those defaults.

6. **Diagnostics in the product. Decided by the manager.** The read-only `jolt` commands are P3.27, with wall-clock fields masked. The test commands stay on the C# side as the oracle. No test command is added to the Ferroan console. Row: P3.27.

7. **Allocators. Decided by the manager: nothing to decide.** The one process-wide temp allocator is a property of the stock joltc that JoltPhysicsSharp 2.19.1 binds. `oxijolt-sys` 1.6.0 gives each `PhysicsSystem` its own. P3.0c adapts the C# backend to that explicit allocator. Ferroan is one region per process, and the physics thread runs one heartbeat at a time. A future multi-region process is a product question, not an allocator limit. No row changes.

8. **`[Startup] physics`. Decided by the maintainer on 26 November 2026.** The shipped default is `ubODE` (`RegionServerDefaults.ini` 313). The Jolt module loads nothing unless the value is exactly `Jolt`. [D9](../DECISIONS.md) does not port ubODE or BulletSim. When the value is not `Jolt` (ubODE, BulletSim, or anything else), Ferroan logs one warning naming the setting and the value and runs Jolt. [D110](../DECISIONS.md) records that and points at D9. Row: P3.2c.

9. **Successful region crossing of a physical object. Decided by the manager.** Failed crossing and out-of-bounds stay P3.56. A crossing that succeeds, including `MotorRunningState` carried to the neighbour, belongs with the avatar crossings that [D38](../DECISIONS.md) leaves for later, in Phase 4. Row: P3.56. No Phase 3 row is added for a crossing that succeeds.

10. **Wind. Decided by the manager.** Wind waits for a later phase. Phase 3 keeps region wind at zero and does not port `IWindModule`. P3.23d still tests `ReactToWind` with an injected sample. Row: P3.23d.

11. **D11 and physics meshing. Decided by the manager.** [D109](../DECISIONS.md) records that physics meshing follows `PrimMesher` and `Meshmerizer` and that `aurora-prim` does not supply physics triangles. [D11](../DECISIONS.md) still supplies viewer-side prim volumes. No shape row uses `aurora-prim`. [ARCHITECTURE.md](../../ARCHITECTURE.md) cites D109 on the `ferroan-physics` row.

12. **How `oxijolt-sys` is built. Decided by the maintainer on 26 November 2026.** The repository default is `JOLTC_PREBUILT=require` without `force`, always with `cross-platform-deterministic` and the pinned SHAs. CI and a default build fetch the SHA-checked archive for x86_64 Linux glibc 2.35, x86_64 Windows MSVC 14.44 and aarch64 macOS 11.0. `JOLTC_PREBUILT=off` builds from source. `JOLTC_LIB_DIR` is refused. The recorded SHAs move with the `oxijolt-sys` version. P3.1 records that beside D8. Linux, Windows and macOS link on PR #323 (`checks (windows-latest)` and `checks (macos-latest)`). P3.1b records the notices and the vendored-fork fallback beside D8. Rows: P3.1 and P3.1b.

13. **Dependency maturity. Decided by the maintainer on 26 November 2026.** Accept `oxijolt-sys` on its current terms: about seven weeks old, one publisher, 11 releases, and it has not moved to Jolt 5.7.0 (14 November 2026). The vendored-fork fallback is beside D8. Row: P3.1b.
