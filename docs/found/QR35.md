# Found while working: QR35

- 26 November 2026, QR35: PostgreSQL password tokens use the process clock on both Ferroan (`pg_when`) and Pin8 (`DateTime.Now` in `PGSQLAuthenticationData.SetToken` and `CheckToken`). `CheckToken` compares that stamp with the session clock (`validity > (CURRENT_DATE + CURRENT_TIME)`). When the process zone and the session zone differ, the stored stamp is already outside the session clock and verification fails on both sides. Aligning the session with the server zone, which is how Npgsql leaves it, is the configuration where verification succeeds. `pg_when` stays on the process clock. No separate bug number: Ferroan matches Pin8.

- 26 November 2026, QR35: A PostgreSQL login that cannot read `postmaster.opts` (`pg_read_file`) or `pg_file_settings` cannot recover the server zone after sqlx's startup `TimeZone=UTC`. `RESET TimeZone` and `SET TIME ZONE DEFAULT` keep the client setting. Role and database settings in `pg_db_role_setting`, and `PGTZ` when `Timezone=` is absent, are applied before those files. The session stays UTC only when none of those name a zone and the files cannot be read (D104). An ordinary login is checked for privilege before the file reads. Only SQLSTATE 42501 is unreadable; any other probe error refuses the connection. MySqlConnector 2.6.2 has no `Timezone=` key, so a MySQL session uses the server zone.

- 26 November 2026, QR35: The MySQL Presence store is still Q26c2. This proof writes `LastSeen` with the same `UPDATE ... LastSeen=NOW()` as `MySQLPresenceData.ReportAgent` and the Pin8 plugin reads that row. It does not add the store.
