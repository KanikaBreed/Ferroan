# Found while working: QR35

- 26 November 2026, QR35: PostgreSQL password tokens use the process clock on both Ferroan (`pg_when`) and Pin8 (`DateTime.Now` in `PGSQLAuthenticationData.SetToken` and `CheckToken`). `CheckToken` compares that stamp with the session clock (`validity > (CURRENT_DATE + CURRENT_TIME)`). When the process zone and the session zone differ, the stored stamp is already outside the session clock and verification fails on both sides. Aligning the session with the server zone, which is how Npgsql leaves it, is the configuration where verification succeeds. `pg_when` stays on the process clock. No separate bug number: Ferroan matches Pin8.

- 26 November 2026, QR35: A PostgreSQL login that cannot read `postmaster.opts` (`pg_read_file`) or `pg_file_settings` cannot recover the server zone after sqlx's startup `TimeZone=UTC`. `RESET TimeZone` and `SET TIME ZONE DEFAULT` keep the client setting. Role and database settings in `pg_db_role_setting`, and `PGTZ` when `Timezone=` is absent, are applied before those files. The session stays UTC only when none of those name a zone and the files cannot be read (D104). An ordinary login is checked for privilege before the file reads. Only SQLSTATE 42501 is unreadable; any other probe error refuses the connection. MySqlConnector 2.6.2 has no `Timezone=` key, so a MySQL session uses the server zone.

- 26 November 2026, QR35: The MySQL Presence store is still Q26c2. This proof writes `LastSeen` with the same `UPDATE ... LastSeen=NOW()` as `MySQLPresenceData.ReportAgent` and the Pin8 plugin reads that row. It does not add the store.

- 26 November 2026, QR35: PostgreSQL accepts a fixed offset (`5.5`), a POSIX zone (`EST5EDT,M3.2.0,M11.1.0`) and a quoted abbreviation (`<+0330>-03:30`). Filtering those characters refused connections Npgsql accepts. `Timezone=` and `PGTZ` are sent as given. Role, database, command-line and file values are taken as stored. The only local check is the length bound `db.timezone`. `SELECT` on `pg_db_role_setting` is checked with `has_table_privilege` before the read, so a login without that privilege still connects and the refusal is not written to the server log. `Timezone=` or `PGTZ` is checked on one connection before the pool starts. The session stays on silent UTC only when `pg_file_settings` itself was readable and named no zone.

- 26 November 2026, QR45: `to_regrole(quote_ident(session_user))` resolves the logged-in role, including a mixed-case name, when `SELECT` on `pg_roles` is revoked, so the role zone still applies and the probe writes no error. The database oid comes from `pg_stat_get_activity`, so revoking `SELECT` on `pg_database` keeps the role zone. `SELECT` on `pg_db_role_setting` is checked before that read; without it the probe falls through. `pg_file_settings.applied` stays true when the command line overrides the file, so a file zone or silent UTC is used only when `postmaster.opts` was also readable. Otherwise the session stays on UTC and the pool logs the D104 warning. `EXECUTE` on `pg_show_all_file_settings()` is checked with `SELECT` on `pg_file_settings` before the file read. `PGTZ=NotAZone` is refused on one connection before the pool starts, the same as `Timezone=NotAZone`.
