# Found while working: QR32

- 2026-11-25, QR32: **Docker smoke companion logout.** PR #256 (Q82) run 45575408222, `live images`, failed three times with `docker: companion LogoutReply was not received`; PRs that contain Q48 but not Q82 pass. The bug is in Q48's harness code and Q82's terrain exposes it. `wait_nearby` (`xtask/src/ferrobot.rs`) did not drive the companion's circuit while Ferrobot's `NearmeWithDetails` ran, and that call holds for Ferrobot's 10 s name timeout because the Ferroan region does not answer `UUIDNameRequest` yet (Q84). With Q82's stored terrain the region sends the companion a reliable `LayerData` burst on arrival; unacknowledged, it is resent every pass. A local Q82 smoke recorded 651 datagrams to the companion in those 10 s, 459 of them resends. An undriven socket kept about 220 small datagrams before the kernel dropped the rest, so the companion's buffer (`net.core.rmem_default` 212,992 bytes) was full when it sent `LogoutRequest`, and the kernel dropped the `LogoutReply`. The region closes the circuit right after that reply, as C#'s `LogoutHandler` does, so the reply is not resent. It is not Docker networking (the grid uses host networking) and not the logout order. Fix: `driven` runs each `NearmeWithDetails` call beside the companion's `drive` in a `tokio::select!`. `a_driven_companion_gets_its_logout_reply_after_a_long_call` floods a driven bot from a fake region during a 1.5 s call and requires the `LogoutReply` the fake sends once; without `driven` it fails every time. `cargo xtask docker smoke` on `feat/q82-default-terrain` failed locally the same way and passes with the fix. The check itself does not change.
- 2026-11-25, QR32: this machine's Docker has no `compose` plugin, so `cargo xtask docker smoke` fails here at `docker compose logs` before Ferrobot runs. The local reproductions skipped that one check in a change that is not committed; CI's Home1 runner has the plugin.
- 2026-11-25, QR32: **macOS flake.** `an_arrival_is_announced_and_the_newcomer_hears_of_the_others` (PR #260, run 45644560629) slept for two frames and asserted that `SendInitialData` had not run yet. The frame thread ticks on the wall clock, so a slow runner can pass four ticks in that sleep. The test now reads the frame counter before the reply is posted, waits for the packets, and asserts at least four frames passed; it fails if `SendInitialData` runs a frame early (checked by changing the wait to three frames). Q46b's `a_terse_update_waits_for_initial_data_and_reaches_every_viewer` had the same "two frames, not yet" pattern twice; it now counts frames the same way and requires the first terse update five frames after the reply (it fails when the wait is shortened). Its re-armed wait now posts the reply before the arrival, which applies it first: with the reply after the arrival, a tick between them would have tested the walk's stop with the wait still over.
