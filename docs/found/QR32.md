# Found while working: QR32

- 2026-11-25, QR32: **Docker smoke companion logout (handed to Q82's coder; not fixed here).** PR #256 (Q82) run 45575408222, `live images`, failed with `docker: companion LogoutReply was not received`; other PRs that contain Q48 pass, so it needs Q82's stored terrain. Cause found in Q48's harness code: `wait_nearby` (`xtask/src/ferrobot.rs`) does not drive the companion's circuit while Ferrobot's `NearmeWithDetails` runs, and that call holds for Ferrobot's 10 s name timeout because the Ferroan region does not answer `UUIDNameRequest` yet (Q84). With Q82's terrain the region sends the companion a reliable `LayerData` burst on arrival; unacknowledged, it is resent every pass. A local Q82 smoke recorded 651 datagrams to the companion in those 10 s, 459 of them resends. On loopback each datagram costs about a kilobyte of receive buffer, so the companion's 212,992-byte socket buffer (`net.core.rmem_default`) is full when it sends `LogoutRequest`, and the kernel drops the `LogoutReply`. The region closes the circuit right after that reply, as C#'s `LogoutHandler` does, so the reply is not resent. It is not Docker networking (the grid uses host networking) and not the logout order. Proposed fix, verified locally: drive the companion's session in a `tokio::select!` beside each `nearby(api)` call in `wait_nearby`, as `roots_scenario` drives the staying bot. `cargo xtask docker smoke` on `feat/q82-default-terrain` failed the same way locally without it and passed with it. The check itself does not change.
- 2026-11-25, QR32: this machine's Docker has no `compose` plugin, so `cargo xtask docker smoke` fails here at `docker compose logs` before Ferrobot runs. The local reproductions skipped that one check in an uncommitted change; CI's Home1 runner has the plugin.
- 2026-11-25, QR32: **macOS flake.** `an_arrival_is_announced_and_the_newcomer_hears_of_the_others` (PR #260, run 45644560629) slept for two frames and asserted that `SendInitialData` had not run yet. The frame thread ticks on the wall clock, so a slow runner can pass four ticks in that sleep. The test now reads the frame counter before the reply is posted, waits for the packets, and asserts at least four frames passed; it still fails if `SendInitialData` runs a frame early (checked by changing the wait to three frames). Q46b's `a_terse_update_waits_for_initial_data_and_reaches_every_viewer` has the same "two frames, not yet" pattern (`frame.rs` "the first frames return early" and "the re-armed wait returns early") and can flake the same way on a slow runner; it has not failed yet.
