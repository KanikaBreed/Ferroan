# Found while working: Q208

- 26 November 2026, Q208: A missing part or a null group sends nothing. A root marked deleted but still in the graph sends one kill to every client. Ferroan's delete is synchronous and sends neither (TB183). `UseTrashOnDelete` is true (`Scene.cs` 271). `DeleteToInventory` calls `DeleteGroupFromScene(false)` at once (`AsyncSceneObjectGroupDeleter.cs` 85–89). The group stays registered until `InventoryDeQueueAndDelete` finishes `CopyToInventory` and calls `DeleteSceneObject` (123–135). The deleter is enabled at `Scene.cs` 881. A second `DeRezObject` for that root reaches `SendKillObject` (`Scene.cs` 4058–4070).
- 26 November 2026, Q208: The delayed kill uses fixed priority 2. C# uses the prioritizer's distance queue (`LLClientView.cs` 4917, `Prioritizer.cs` 85–118). Only the order among other queued updates differs.
- 26 November 2026, Q208: `category` on both property blocks is 0. SQLite does not store `Category`. A part loaded from XML or an OAR carries `<Category>` (`SceneObjectSerializer.cs` 1045) until restart, and `ObjectPart` has no field for it.
- 26 November 2026, Q208: `DeRezObjects` skips every attachment. The god test is `!sp.IsGod || action != Return || action != Delete` (2915–2918), and the two action comparisons cannot both be false. Ferroan does not delete attachments (TB184).
- 26 November 2026, Q208: `DeleteGroupFromScene` sends `KillObject` for the root and then `SendEntityUpdate` with `PrimUpdateFlags.Kill` (`SceneObjectGroup.cs` 2983–2986). The viewer gets two `KillObject` packets for that root. That is the path this capture records.
