# Decisions

Settled decisions. To change one, open a PR that edits this file and says why.

| # | Decision | Chosen | Notes |
| --- | --- | --- | --- |
| D1 | Do the SLua engine plan in today's C# server first? | Yes. Run Linden's SLua engine in Tranquillity, and keep using C# until Ferroan is stable | Phase 4 reuses that work's C interface and conformance suite |
| D2 | Mixed grids or one big switch | Dual support until the switch: Rust and C# pieces run on the same grid | Every phase keeps wire compatibility with the C# server |
| D3 | Where the code lives | This repository, run by the team | Public since 17 November 2026 |
| D4 | Licence | GPL-3.0-or-later for the project; each ported or copied file keeps its original notices and references | Changed from MPL-2.0 on 17 November 2026 so Aurora Viewer's Rust code can be reused. BSD, MPL-2.0, Apache-2.0, MIT and LGPL-2.1 sources may all be combined into a GPL-3.0 work. Ferroan code cannot flow back into Tranquillity's BSD/MPL tree ([PORTING.md](PORTING.md)) |
| D5 | Team | Volunteers | Calendar time depends on hours given ([PLAN.md](PLAN.md)) |
| D6 | Async runtime and HTTP stack | tokio for networking and services; axum and hyper for HTTP servers, reqwest as client. The region frame loop, Jolt and the SLua engine run on their own threads | tokio is the most widely used runtime, and axum, hyper, reqwest and sqlx build on it. A frame loop needs a fixed tick, and both native libraries expect a thread of their own |
| D7 | Feature freeze in C# | Freeze each part's features once its Rust phase starts | Bug fixes still go into both |
| D8 | Native libraries | Only Jolt and Linden Lab's SLua engine | A third needs its own decision here |
| D9 | Physics engines | Jolt only | BulletSim, ubODE, POS and basic physics are not ported |
| D10 | One script engine | Linden's SLua engine runs LSL, SLua, OSSL and bot functions | Phlox's VM and YEngine are not ported; YEngine's language extensions are unsupported |
| D11 | Reusing Aurora Viewer | Reuse Aurora's Rust crates where the code is the same on both ends: LLSD, message template code generation, prim volumes | Copied files keep Aurora's notices and record the Aurora revision. Viewer-side logic is a reference for the region server, whose circuit differs. `ferroan-bot` adapts Aurora's login, XML-RPC and circuit because the bot is a viewer |
| D12 | Where code comes from | Rust code Aurora already has (D11) comes from Aurora. C# code Aurora lacks is ported from OpenSim-NGC/libopenmetaverse, the exact OpenMetaverse build Tranquillity uses, or from Tranquillity itself | libopenmetaverse and Tranquillity are also the byte-level oracles for every fixture. Revisions are pinned in [REFERENCES.md](REFERENCES.md) |
| D13 | Rust first | All Ferroan code is Rust, including tools, scripts, test helpers and CI tasks (`cargo xtask`). Another language needs an entry here with the reason | Allowed now: the C# oracles under `tools/*-oracle` (reference, schema, config, http and asset; each must run OpenMetaverse, Nini or Tranquillity C# code to produce the expected result) and the Tranquillity capture patch, because they must run or change C# code. The live harness builds and runs Tranquillity but is itself Rust; Jolt and the SLua engine (D8) |
| D14 | SQLite inside sqlx | `ferroan-db` links `libsqlite3-sys` with SQLite bundled, so the SQLite driver builds on Linux, Windows and macOS without a system package. MySQL and PostgreSQL use sqlx's Rust protocol code and add no native library | This is the database driver named in D6. It does not loosen D8: Jolt and SLua remain the only native libraries in the physics and scripting crates. `ring`, which rustls uses, is D16 |
| D15 | Automation first | A check a program can make is made by a program. Region and service behavior is checked by `ferroan-bot` scenarios, and by Ferrobot sessions (D17), in the live harness against a local Tranquillity region, in CI. A person with Firestorm checks each phase gate, following `docs/MANUAL_CHECKS.md` | Volunteers are few and viewer sessions are slow to repeat. The bot sees what the server sends, not what Firestorm draws, so the phase-gate check stays |
| D16 | rustls crypto provider | `ring` is allowed. `reqwest` and `sqlx` reach TLS through `rustls`, and `rustls` uses `ring` | `ring` is already in `Cargo.lock` through those crates. It is not a physics or scripting library and does not loosen D8 for `ferroan-physics` or `ferroan-scripting`. No other native crate is pulled in with it |
| D17 | A second test client | Ferrobot ([BlackBox-Roleplay-Systems/Ferrobot](https://github.com/BlackBox-Roleplay-Systems/Ferrobot), GPL-3.0) is allowed as a test client beside `ferroan-bot`. It is pinned in [REFERENCES.md](REFERENCES.md), built from that revision, and run as a separate process driven through its signed HTTP API. Ferroan code does not depend on it or copy from it | `ferroan-bot` stays the scenario and capture client: it is scripted step by step and its traffic is the fixture. Ferrobot is a different client implementation (its own login, circuit, event queue, relog and command code; it shares only Aurora's LLSD and message crates), so it catches server bugs that `ferroan-bot` and the server agree on by accident. It also covers long sessions and features `ferroan-bot` lacks: IM, groups, friends, inventory and teleport offers. A Ferrobot bug is reported to Ferrobot, never patched or worked around silently in Ferroan |
| D18 | Containers, monitoring and logs | Every Ferroan server ships as a container image, laid out like Tranquillity's (`/app/config`, `/app/data`, `/app/logdata`, the same configuration files mounted in). Monitoring has two layers. First, the endpoints Tranquillity already has, in the same forms: `/simstatus`, `/monitorstats/<region id>`, the managed stats at `ManagedStatsRemoteFetchURI` with its password, and `/SStats`. Second, additions that change no protocol: Prometheus `/metrics`, `/healthz` and `/readyz`, and structured logs. The additions are configured in a `[Monitoring]` section that C# ignores, and are off unless set. Logs go to stdout in containers, so `docker logs -f` and any Docker logging driver stream them, and to files under `LOGDIR` as Tranquillity does. Tranquillity's remote console (`/StartSession`, `/SessionCommand`, `/ReadResponses`, `/CloseSession`, with `ConsoleUser` and `ConsolePass`) streams logs and takes commands in the same forms. OpenTelemetry (OTLP) export of logs, metrics and traces, off unless configured, is the hook for whatever log system an operator runs. An OpenTelemetry Collector adapter in `deploy/monitoring/collector/` has ready configs for Loki, OpenSearch, SigNoz, Graylog and Splunk. No log line carries a password, session id, circuit code or capability URL | Operators' existing dashboards and scripts keep working against Ferroan, and container deployment matches what Tranquillity already ships. The additions give per-sim status (agents, frame time, UDP and resends, event queue, HTTP, database) without a C# equivalent to match. The metrics listener binds to loopback unless configured. Images are built in CI. Publishing them to a registry waits for the maintainer |
| D19 | Invalid circuit timing inputs | P2.0a3 uses measured server-ping RTTs; a completion received before any server ping leaves the initial estimate unchanged. Timer configuration must be positive and fit signed 32-bit milliseconds; zero RTO values retain C#'s documented default-selection behavior | At `8583218`, C# otherwise subtracts a zero-initialized timestamp for an unsolicited completion and accepts signed timer values that can be negative or overflow. These cases do not describe a measured round trip or valid timeout. Ferroan rejects invalid configuration and ignores the unavailable RTT sample. Valid sent-ping filtering, timer defaults/units and inactivity behavior remain source-derived; packet and INI formats do not change. Tests and the region guide make this boundary explicit |
| D20 | Trusted-host parsing and bounded DNS refresh | Follow fixed C# at `40432e0`: parse addresses before URI/host-port forms, ignore IPv6 zones, combine both aliases in Security and Network, and warn and ignore unusable entries without looking up an empty name. Resolve names at startup and, after an untrusted call, at most once a minute; failed or empty lookups retain that name's last addresses | TB5 is on `develop` at `9e464d5395` and `5e1e9979c0` (PR #429), brought in by Pin4. Pin3 first pinned the same fix on `dev-build`. This replaces the `8583218` ambiguous-host startup rejection and startup-only DNS policy accepted on 19 November 2026. The maintainer approved this revision on 19 November 2026 (Pin3, #56). Ferroan retains bounded configuration (256 list entries plus Network.hostname, 2048 bytes each), a 4096-entry total address-cache bound and five-second lookup batches. Excess startup input fails; refresh resource/timeout failure retains the prior snapshot. Concurrent callers use the last published snapshot while one caller refreshes; cancellation does not start an unbounded stream of lookups. [Pin3 source review](PIN3_REVIEW.md) and the C# trust observations document the change |
| D21 | The Tranquillity pin while the maintainer's C# fixes wait for upstream review | The pin may be a commit on `dev-build` in the maintainer's fork, [KanikaBreed/OpenSim-Tranquillity](https://github.com/KanikaBreed/OpenSim-Tranquillity/tree/dev-build): upstream `develop` with the maintainer's open OpenSim-NGC PRs merged in, unchanged. [REFERENCES.md](REFERENCES.md) names the fork, the branch, the commit and the PRs it carries. Each pinned commit is tagged `ferroan-pinN` on the fork, so it stays reachable when `dev-build` is rebuilt | Review upstream takes time, and Ferroan should port and capture from the fixed behavior instead of reproducing bugs already fixed (TB5 to TB9). The branch carries only PRs opened upstream, so everything in the pin is on its way to `develop`, and nothing Ferroan-only is added to it. When a carried PR changes in review or merges, `dev-build` is rebuilt on the new `develop` and the pin moves the usual way. Once every carried PR has merged, the pin goes back to a `develop` commit. Pin4 is that return: OpenSim-NGC `develop` `f67db54399`. A PR rejected upstream is dropped at the next move, and its ledger row goes back to Open |
| D22 | Root-login replacement order | On a successful replacement, verify presence before accepting the new circuit, and send GridUser `LoggedOut` from the dispatcher after that HTTP response. On a failed Presence verify of an existing root, close that root and wait for its logout inside the CreateAgent budget, then refuse | C# `NewUserConnection` closes the old root before `VerifyUserPresence` (`Scene.cs` around 4308–4370 at `40432e0`). Ferroan keeps the success-path order: `replacement_waits_for_root_writes_and_old_generation_cannot_report_again` requires verification to wait behind in-progress root reporting, and a `LoggedOut` before accept can mark the new session offline. A failed verify of a root still closes it and fires `LoggedOut` and Presence logout before the refusal returns. Close-before-verify is intentional C# behavior, not a Tranquillity bug, so no TB row is filed. Recorded by Q10i (#81). The maintainer accepted the Rust order on 19 November 2026 |
| D23 | Where the new asset system keeps asset bytes and its catalog | Asset bytes live in a storage service reached through a storage plugin, and the catalog lives in SQL. The catalog holds each asset's id, the SHA-256 of its bytes, its type, name, description, creator, class, state and history. Storage plugins: SeaweedFS through its native volume API, and any S3-compatible store (for example Garage, Cloudflare R2, Backblaze B2, AWS S3, or SeaweedFS's own S3 gateway). A built-in local backend with SQLite stays for the smallest standalones. Catalog databases: SQLite, and MySQL or MariaDB. On MySQL and MariaDB the server checks at startup that the catalog uses `utf8mb4`, strict SQL mode and InnoDB, and refuses to start otherwise. PostgreSQL is not a catalog database for this system | SeaweedFS (Apache-2.0, written in Go) runs as its own process. Ferroan reaches it only over HTTP and never links it, so it is not a native library and does not loosen D8. Its volumes pack many small assets into large files behind an in-memory index, so one box serves millions of assets, and a grid grows by adding volume servers and turning on replication without the asset server moving data. With the native plugin, the catalog records each blob's SeaweedFS file id, so SeaweedFS's filer and its metadata store are not needed. Chosen by the maintainer on 21 November 2026, after a probe of Tranquillity's FSAssets at `f67db54399` measured how it loses and damages assets. The new system is a new backend behind the same asset HTTP routes, so C# regions and other grids see no change. Its storage is Ferroan's own, and a grid moves to and from Tranquillity's backends by import and sync. The three Tranquillity backends (P1.A1 to P1.A3) are still ported, for grids that keep them and as import sources. The rest of the design is still being discussed and has no tasks yet |
| D24 | What an asset id means in the new asset system | Each id is bound to the SHA-256 of its bytes at creation and never overwritten. "Stored" is answered only once the bytes are durable and the catalog row committed. Every read is checked against the hash, and a mismatch is answered as missing. Content is checked by type on the way in, and fails with an error the uploader sees. Any copy whose bytes match the hash may repair a missing or damaged one. The creator may replace a confirmed-damaged asset with new bytes under the same id, and so may a grid administrator when the creator has left or is a Hypergrid visitor, both recorded in the asset's history. A missing or damaged texture shows as a bright pink placeholder: a Ferroan region sends the placeholder's own id to the viewer and leaves the stored object unchanged | Settled by the maintainer on 21 November 2026. The FSAssets probe (TB22 to TB25) found stores reported as done that were not, and damage served with HTTP 200 that no store could repair. Sending the placeholder's own id keeps viewers from caching pink under the real texture's id. Design: [ASSET_SYSTEM.md](ASSET_SYSTEM.md) §2, §5 and §6 |
| D25 | How viewers get assets | Four delivery modes: `open` (anyone with the UUID, as Second Life's CDN; the default), `session` (a logged-in session's token), `scene` (only what the region has shown that avatar; built once Ferroan has its own regions) and `region` (through the region's caps, as OpenSim does today, and always for C# regions) | Settled by the maintainer on 21 November 2026. No mode stops a viewer copying what it is sent, and the operator guide says so. Design: [ASSET_SYSTEM.md](ASSET_SYSTEM.md) §8 |
| D26 | Clean-up of assets | Assets have a class (`original`, `foreign`, `bake`, `maptile`, `remote`). Deletes leave tombstones that can be restored during a grace period. Grid owners write their own clean-up policies, within floors the server enforces: nothing referenced or pinned is purged, quarantine comes before purge for at least 7 days, an original must be unreferenced for at least 90 days, a new policy reports before it acts, and tombstone rows are kept. Owners may raise the floors, never lower them below the hard minimums | Settled by the maintainer on 21 November 2026. Originals are only reported until the reference index exists (AS11). Design: [ASSET_SYSTEM.md](ASSET_SYSTEM.md) §7 |
| D27 | Moving a grid to and from the new asset system | Import from every Tranquillity backend, from OAR and IAR archives and from region cache files, with a dry run that writes nothing and reports the store's health. Two-way sync with a Tranquillity backend (a full copy, then shadow, cut-over and write-through), and an export that C# Robust serves. Packaged as a one-command Docker Compose bundle (`ferroan-robust`, SeaweedFS, SQLite) for small grids | Settled by the maintainer on 21 November 2026. This is how the Phase 1 gate's "switch back at any time" holds for a backend whose storage is Ferroan's own (D23). The return trip loses what the C# backends cannot hold: classes, history and tombstones. Design: [ASSET_SYSTEM.md](ASSET_SYSTEM.md) §10 and §11 |
| D28 | Hypergrid security and content as separate layers | Who may call (security) and how content moves (content) are settled separately per pair of grids: V1/V1, V2/V1 or V2/V2. V1 security with V2 content is not offered. Over any content version: whether content may leave is decided by the creator's export permission and the grid's export policy, the stricter winning, and the visitor is told when content will not be sent home; content going home is retried until accepted; foreign copies record their origin and are kept while used on this grid. V2 content adds manifests with hashes, unchanged bytes with creator details as signed metadata, existence by hash, and a `remote` record at home for content that stays on another grid | Settled by the maintainer on 21 November 2026, after the Hypergrid content probe (TB26). Proposed for Hypergrid V2 itself in Tranquillity `Docs/feature/hypergrid-v2/` §14. Design: [ASSET_SYSTEM.md](ASSET_SYSTEM.md) §9 |
| D29 | XAsset bugs that lose or hide a row | TB27 to TB30 and TB33 have no viewer or other server that needs the broken result. Ferroan stores on the MySQL transaction (TB27), reads `XAssetsMeta` for exists (TB28) so a chained migrate keeps the asset (TB33), returns the PostgreSQL metadata page with `LIMIT` count `OFFSET` start (TB29), and on PostgreSQL deletes the meta row and the data row when that hash is unused (TB30). MySQL delete still removes only the meta row, which is what its statements do. `live assets --backend xasset` lists those ids until the pin moves. TB19 and TB20 on `AssetService` stay matched | The C# fixes are pending upstream. Recorded by Q22c |
