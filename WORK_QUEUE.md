# Work queue

The project manager orders Ferroan's work here. [TASKS.md](TASKS.md) records what each task is and the evidence that it is done. This file says what to do next and in what order.

## How the coder uses it

The coder works unattended, through the queue, as far as it can get. The maintainer pauses or restarts it.

1. Take the first item marked `READY` whose `after` item is `DONE`, and whose TASKS.md dependencies are all `DONE`. Do not start anything else: not other plan items, not B04.
2. Work it the way [AGENTS.md](AGENTS.md) describes: a task worktree, the C# reference at the pinned revision, the checks, and a PR using the template.

   **Review before the PR** (the maintainer, 24 November 2026: "they do work, you code review, they fix the issues then they make pr"). Commit the item on your branch but do not push or open a PR. Stop and hand the branch to the manager (worktree, branch, commit, base, checks run). The manager reviews the diff and sends findings; fix them, then push, open the PR and merge as rule 5 says. A docs-only `BLOCKED` split needs no review and goes straight to a PR.
3. Prove it by automation. Use unit and fixture tests against bytes captured from C#, `ferroan-bot` scenarios, and Ferrobot checks once Q10 is done, all in the live harness. A step that only a person can check is recorded as pending, never as passed.
4. Set the item to `IN PROGRESS` with the branch when you start. In the same PR, set it to `DONE (this PR)` and fill the TASKS.md row with the evidence you have before you open the PR: the tests, the local live runs and their output. Do it in the commit you open the PR with. Do not push a later commit only to add the PR number, CI links or durations: CI links and the final result go in the PR description, which you can edit without starting a run. The manager replaces `this PR` with the number afterwards.
5. Merge with `gh pr merge --auto --squash`. `main` requires the Linux, Windows, macOS and live checks, so the PR lands only when they pass. Never use `--admin` and never bypass the protection. If a check fails, fix the cause. After three attempts at the same failure, set the item to `BLOCKED`.

   **One push per real change.** Every push starts the whole CI and live harness again (about 25 minutes) and cancels the run already going. Push only a code or content fix. A failure you judge a flake is retried with `gh run rerun <run-id> --failed`, which reruns only the failed jobs, never with a new commit. Merge `origin/main` into your branch only when the PR conflicts with it or needs something that just landed, not because `main` moved: `main` does not require branches to be up to date.
6. If an item is wrong, too big or blocked, set it to `BLOCKED`, add the reason and a proposed fix or split under it, and open that change as its own PR. Do not change an item's scope yourself. Then go on to the next item that can be taken, skipping items that depend on the blocked one.
7. Gates (`G0`, `G1`, `G2` …) are the maintainer's Firestorm checks. Never mark one. Items that depend on a gate wait, and the rest go on.
8. Write anything you find that is not your item (a flaky test, a C# bug, a gap in a row) in `docs/found/<item>.md`, the file named after the queue item you are working (`docs/found/Q46b.md`). Work with no queue item (a manager or docs-only PR) uses the last part of its branch name (`docs/found/queue-nov25.md`). If the file does not exist, create it with the heading `# Found while working: <item>`. Add each finding at the end as one bullet in the old form, `- <date>, <item>: <text>`. Write only in your own item's file. The "Found while working" list below is closed (25 November 2026) and stays as it is. No two open PRs work the same item, so no two PRs touch the same file, and these notes no longer conflict. A C# bug also gets a row in [docs/TRANQUILLITY_BUGS.md](docs/TRANQUILLITY_BUGS.md). The manager turns findings into items and adds `(queued as <id>)` to each entry it takes; entries are never deleted. A flaky check is never retried silently: record it, but without a push of its own. Note it in the PR description when you rerun, and add it to your item's file in the next commit you push anyway (or leave it in the PR description, and the manager copies it there).
9. Stop only when no item can be taken, and say why.
10. **Two coders.** The manager may run two queue coders at once (the maintainer agreed on 19 November 2026). Then each coder's brief from the manager names the one item it takes, on its own track (usually one on the region track, one on Phase 1 services), and that brief overrides rule 1's "first item" for that coder. Never take an item another coder's brief names, or one marked `IN PROGRESS`. Both edit TASKS.md, WORK_QUEUE.md and the guides: when `main` moves under you, merge `origin/main` into your branch and keep the other coder's changes.

Only the manager adds, removes, reorders or rewrites items. The coder changes only the Status column, the notes under an item, and its item's file in `docs/found/`.

Status values: `READY`, `IN PROGRESS`, `BLOCKED`, `DONE`, and `EXTERNAL` (an outside contributor has claimed the item's issue; skip it, and treat it as done only when its TASKS.md row is `DONE`).

Items that name a GitHub issue are open to outside contributors too, but the coder does not wait for them. When such an item comes up, check its issue first (`gh issue view <n> --json labels`). If it is labelled `claimed`, a contributor has it: skip the item and go on. If not, it is the coder's: add the `claimed` label, post one comment on the issue ("The project's queue coder is taking this, on branch `<branch>`."), and work it as usual, with `Closes #<n>` in the PR. An item that names several issues is taken one issue at a time, in the order listed. This is the only issue comment the coder posts.
